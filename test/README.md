# GeoChess host tests

Chess engines fail quietly. A move generator that is wrong in one
position still plays a whole game without crashing, and the bug only
shows up as the engine occasionally doing something illegal. These
tests exist so that class of bug is caught mechanically instead of over
the board.

Everything here builds with an ordinary host compiler against
`../src/geochess-ai.h`. **cc65 is not required** and nothing here
touches GEOS: the engine is plain C with no platform dependencies, so
it can be exercised on the desktop at a few million nodes a second
rather than on a 1 MHz 6502.

## Running

    ./run.sh          # POSIX
    run.bat           # Windows

Both compile into `build/` and report per-suite pass or fail, exiting
non-zero if anything failed. Override the compiler with `CC=clang`, or
the interpreter with `PYTHON=...`.

Python 3 is needed for one generated suite (see `savetest` below); the
other five are plain C.

## The suites

### `perft.c` — move generation

Counts leaf nodes to a fixed depth and compares against the published
reference values. This is the standard way to validate a chess move
generator: the counts are exact, so a single illegal or missing move
anywhere in the tree changes the total.

Includes a FEN parser and a `divide` that prints per-move subtotals,
which is how you bisect a mismatch down to the offending move.

| position | depth | nodes |
|----------|-------|-------|
| start | 5 | 4,865,609 (includes 258 en passant captures) |
| Kiwipete | 4 | see note |
| position 3 | 4 | 43,238 |

**Note on Kiwipete depth 4.** The published figure is 4,085,603 and
this engine produces 4,074,224. The difference is exactly 11,379 and is
fully accounted for: that depth contains 15,172 promotion nodes, and
this engine promotes only to a queen, so each collapses to one node
(15,172 − 15,172/4 = 11,379). Under-promotion is a deliberate omission,
not a move generation defect. If you ever implement it, this expected
value becomes the reference 4,085,603.

### `rules.c` — castling and en passant

Position-by-position checks of the two rules that carry state outside
the piece placement. Castling out of, through and into check; castling
while the rook is attacked (legal) and while the square the king
crosses is attacked (not); rights withdrawn by a king move, a rook
move, and a rook captured where it stands. For en passant: the target
appears only after a double push, expires after any other move, and the
capture removes a pawn that is not on the destination square.

Includes the horizontal pin — an en passant capture removes two pawns
from the same rank at once, so it can expose the capturing side's own
king even though neither pawn was pinned.

### `clickpath.c` — the front end's path into the engine

Drives the engine exactly the way `HandleBoardClick` does: build a move
from board row and column, format it into `user_move`, commit with
`playerMove`. Confirms castling and en passant work through that path
and, importantly, that diffing the board finds every square a move
changed — four for castling, three for en passant. The display relies
on that count being right.

### `search.c` — the engine playing

The only suite that exercises `aiMove` and `SearchPosition`. Plays 400
games of random legal moves against the engine and checks after every
ply that the position is valid, that the side that just moved did not
leave its own king capturable, that `engine_state` agrees with
`ChessStatus`, and that castling rights are never held without the king
and rook actually being home.

### `selfplay.c` — invariants at volume

3,000 random-versus-random games, around 800,000 plies. Counts the
castles, en passant captures and promotions it actually reached, so you
can see the rare paths are being hit rather than assume it. Every tenth
move is made and unmade first and the whole position compared byte for
byte, which is what catches an incomplete `ChessUnmake`.

### `savetest` — the saved game format

Generated by `mksavetest.py`, not checked in.

The pack, validate and unpack code lives in `geochess.c`, which cannot
be compiled on the host: it includes `<geos.h>` and declares the menu
resources as `const void`, which only cc65 accepts. Rather than keep a
second copy here that could silently drift, the generator extracts
those functions from the sources and wraps them in a harness, so what
is tested is what ships.

Round trips a fresh game and a mid-game position with castling rights
spent and an en passant target live, then feeds the validator eleven
kinds of damaged record — bad magic, wrong version, impossible piece
codes, a missing king, two kings, a pawn of the wrong colour, out of
range fields — and checks each is refused. Also checks that a file
claiming castling rights its own piece placement cannot support has
those rights withdrawn on restore.

## Adding to these

The engine has no I/O and no global setup beyond `engine_init()`, so a
new test is a `main()` that sets up `board[]`, `side`, `castle_rights`
and `ep_square`, calls into the engine, and returns non-zero on
failure. Add the file name to the list in `run.sh` and `run.bat`.

Two things to know when writing one:

- `board[]` is a 0x88 array. Only the 64 squares where `(sq & 0x88)`
  is zero are playable; the other columns hold the positional score
  table copied from `starting_board` and are never read as pieces.
  `engine_init()` seeds them, so compare against that rather than zero.
- Perft counts are only meaningful at depths where no promotion
  occurs, unless you adjust for queen-only promotion as `perft.c` does
  for Kiwipete.
